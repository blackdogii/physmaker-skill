# 做事方法論(通用,任何專案適用)

## 完成任務的兩種方式

拿到一個具體任務時,先判斷屬於哪一種,選定後認真執行到底,不能兩種都跳過、憑自己想像直接動手:

1. **架構討論拆解**:跟小威把架構、內容、各種細節先討論清楚,拆解成明確步驟,再照著做。適合公司內部規格明確、獨特的功能,或已經有明確交接文件(例如既有的 PRD、架構文件、handoff 規格)的情況。
2. **調研統整模仿**:蒐集網路上各種相關資訊,統整歸納分析,去蕪存菁後做出一個更好的版本。適合「很氾濫的東西」——市面上一搜就有大量現成範例、已經有成熟慣例的常見功能或工具(例如：排座位產生器、抽籤/隨機挑選工具、QR Code 產生器、計時器、單位換算器、密碼產生器……這類任何領域都可能出現的通用小工具)。

**判斷原則**:開工前先問自己「這個東西獨特到需要跟小威一起設計架構,還是氾濫到网路上一大堆現成範例可以參考?」選錯方法是常見失敗模式——曾經在 PhysMaker 專案的「教學瑞士刀」任務上,因為跳過調研直接憑自己想像刻,被評為「爛到不行」(功能陽春、設計感也差)。

## 走「調研統整模仿」時的具體步驟

1. 用 WebSearch 搜尋「best + 這個工具類型 + tool/generator + 年份」之類的關鵜字,找出市面上 3-5 個受歡迎/知名的實作。
2. **品質信號要用實際指令查證,不能只看搜尋結果標題/摘要判斷「熱門/知名」**:例如 GitHub repo 要用 `gh repo view` 實際查 star、fork、最後更新時間再比較,不能因為搜尋結果排前面或標題聽起來對就當作可信來源直接採用——曾經在 PhysMaker「社群小編 skill」任務上,第一版只憑搜尋摘要就把一個其實不存在的 repo 寫進參考清單,被小威退回要求重做。
3. **在地化敏感的題目,不能只調研到通用/英語框架就套用在地場景**:凡是跟語言、市場、文化、平台生態相關的任務(例如社群經營、文案、法規、消費習慣),除了查現成的工具/skill 之外,還要另外實地查證目標市場的真實做法、案例、業界討論——用自己的推理把外語框架「翻譯」成在地版本,不等於真的調研過在地實務,一樣是同一個「社群小編 skill」任務的教訓:第一版只把英語 B2B SaaS 框架套繁體中文,被要求「上 GitHub 和社群網站多做功課」才重新查了台灣本地案例。
4. 分析它們的**功能清單**(哪些是使用者已經預期會有的必備功能、哪些是加值的進階功能)跟**介面/互動慣例**(這類工具的使用者已經被市面上的做法教育成期待什麼樣的操作方式——例如抽籤類工具幾乎都是「轉盤」視覺而不是純文字結果,這種慣例不遵守會顯得陽春)。
5. 統整、去蕪存菁,決定這次要做的功能範圍與介面設計,不用照單全收每個競品的每個功能,但核心的、幾乎每個競品都有的功能不能省略。
6. 完成後的報告要列出調研參考了哪些做法、做了哪些取捨跟為什麼。
7. **邊界宣告(必須)**:報告調研結果時,要明確區分「我實際完整讀過內容的」跟「我只看過標題/摘要/搜尋結果片段,沒有點進去細讀的」。不能讓使用者誤以為每一條都是我親自讀完的第一手資訊。判斷某個 repo/文章品質有疑慮時,也要講清楚這個疑慮是根據什麼證據(例如:看過完整內容 vs. 只是根據間接跡象合理懷疑),沒做過的查證(例如沒去看 star-history 曲線圖)要明講沒做,不要含糊帶過。

## 通用反 AI 芭樂樣板設計原則(整合自 Anthropic 官方 `frontend-design` skill)

不管是哪個專案,寫使用者會看到的介面之前,先想清楚「這是什麼性質的頁面/工具,設計語言該偏向哪個方向」,不要預設套用最保守、最無個性的樣板。

**AI 生成設計目前公認會落入的三種樣板**(Anthropic 官方 calibration 資料,除非需求明講否則不要落入):
1. 暖米色背景(接近 `#F4F1EA`)+ 高對比襯線大標題 + 赤陶色強調
2. 近黑背景 + 單一螢光綠或朱紅色強調
3. 報紙式版面:細線分隔、零圓角、密集多欄排版

這三種都是「合法但預設」的做法,不是為這個需求量身訂做的選擇。如果需求本身明講要其中一種,就照做;如果需求沒指定,不要把這個自由度用在這三種樣板上。

**其他要避開的芭樂樣板**:
- 白底 + 黑字 + 灰色方框卡片,零色彩個性,跟隨便一個範本網站長得一模一樣(教學瑞士刀第一版就是這個問題)
- 沒有正當理由時還在用系統預設的通用藍/灰配色
- 置中三張長得一模一樣的卡片這種芭樂版面
- 用大量 emoji 取代真正的視覺設計思考
- 沒有動態、沒有互動細節的純靜態列表,即使這類工具的使用者已經被市場教育成期待某種動態互動(轉盤動畫、即時預覽等)

**動工前的流程(兩階段,做完再寫程式)**:
1. **先寫一份簡短設計計畫**,不要直接寫程式:色票(4-6 個具名 hex 值)、字體(至少兩種角色:有個性但克制使用的展示字體、搭配的內文字體)、版面概念(一句話描述+文字草圖)、一個「簽名元素」(這個頁面會被記住的那個獨特之處)。
2. **拿這份計畫對照需求自我批判一次**:如果哪個部分讀起來像是「換成任何類似頁面都會得到一樣的答案」,而不是為這個具體需求做的選擇,就修改它,並說明改了什麼、為什麼。確認過設計計畫真的有獨特性之後才開始寫程式,並嚴格照計畫走。

**克制原則**:把「大膽」留給一個地方就好——讓簽名元素當那個唯一讓人印象深刻的東西,其他地方安靜克制,砍掉任何不服務這個需求的裝飾。但完全不冒險本身也是一種風險。無論選哪個方向,底線要顧到:響應式到手機寬度、鍵盤 focus 可見、`prefers-reduced-motion` 有處理。

**如果專案本身已經有既有的視覺語言/設計系統**(品牌色、字體、既有頁面的風格慣例),新頁面優先沿用既有慣例,不要發明新風格,連上面這套「設計計畫」流程都要先套用「這個網域已經有的風格」當起點——這部分屬於該專案自己的規則,通常會記錄在該專案自己的 skill 或設計文件裡,開工前應該先確認該專案是否有這類文件。

## 動畫決策速查(濃縮版)

寫任何動畫前,先過這三關:

1. **該不該做動畫?** 使用者一天會看到幾次這個互動?100+ 次/天(鍵盤快捷鍵、常用切換)→ 完全不要做動畫;數十次/天(hover、清單捲動)→ 拿掉或大幅簡化;偶爾(彈窗、抽屜、提示)→ 標準動畫;第一次/罕見(引導流程、慶祝效果)→ 可以加點驚喜。**鍵盤觸發的動作絕對不要加動畫**,會讓介面感覺變慢。
2. **easing 怎麼選?** 進場/退場 → `ease-out`;畫面內移動/變形 → `ease-in-out`;hover/顏色變化 → `ease`;等速運動(跑馬燈、進度條)→ `linear`。**絕對不要用 `ease-in`**(開頭慢,會讓介面感覺遲鈍)。CSS 內建的 easing 太弱,盡量用自訂 cubic-bezier(例如 `cubic-bezier(0.23, 1, 0.32, 1)` 當強力 ease-out)。
3. **速度多快?** UI 動畫盡量壓在 300ms 以內:按鈕按壓回饋 100-160ms、提示框 125-200ms、下拉選單 150-250ms、彈窗/抽屜 200-500ms。越快的動畫感覺越靈敏。

**若這個環境有裝 `emil-design-eng`(動畫/UI 打磨完整哲學:easing、spring、clip-path、手勢拖曳細節),遇到動畫決策優先叫用它深入判斷；沒裝的話,上面這份濃縮版已經是 Plan B,足以應付大多數情況,不用因為缺那個 skill 就卡住。**

## 無障礙必查(濃縮版)

出任何使用者會操作的介面前至少確認:
- 所有互動元素都能用 Tab 鍵到達、有清楚可見的 focus 樣式
- 圖片有 `alt`、表單欄位有對應的 `label`、純圖示按鈕有 `aria-label`
- 狀態(選取中、鎖定中、錯誤)不能只靠顏色表達,要有文字或圖示輔助
- 文字對比度足夠(一般文字至少 4.5:1)
- 不要用 `div`/`span` 模擬按鈕,互動元素用真正的 `<button>`/`<a>`

**若這個環境有裝 `frontend-ui-engineering`(含 `references/accessibility-checklist.md` 完整 WCAG 清單),需要螢幕閱讀器/ARIA live region/自動化測試工具這類更深入的檢查時優先叫用它；沒裝的話,上面這份濃縮版是 Plan B,涵蓋最常踩雷的幾點。**

## 手動限定的設計類 skill(這個環境裝了才有效;沒裝不影響上面各段濃縮版/內建判準正常運作)

以下都是「有裝才優先用、沒裝就走本檔案內建的 Plan B」，不是必要依賴：

- `emil-design-eng`——動畫/UI 打磨完整哲學(easing、spring、clip-path、手勢拖曳細節)
- `apple-design`——手勢驅動 UI、彈簧動畫、材質透明度、Apple 風排版
- `frontend-ui-engineering`——production-grade UI 工程慣例,含 `references/accessibility-checklist.md` 完整 WCAG 清單
- `ui-quality`——依任務按需路由到 UI 打磨、色彩、字體、版面、無障礙、整體 review 與 UX 文案參考
- `review-animations`/`pick-ui-library`/`prototype`——動畫嚴格審查、UI 函式庫選擇、多版本原型比較
- `gsap`——按需路由到 GSAP core、timeline、ScrollTrigger、plugins、performance、frameworks、React 與 utils 參考(只在已經決定使用 GSAP 時查)
