# save：知識庫蒸餾與整理

取代並整合原本未上線的 `end-task-knowledge-curation`，同時把「每日 08:00 由 Codex 整理」這行原本沒有規格的工作流正式收進來，變成本技能的 consolidate 模式。

## 兩種模式

- **capture**（預設，互動對話中最常用）：把當次任務／對話的新資訊安全寫入 `01-收件匣/`。
- **consolidate`**（每日排程或按需手動觸發）：把收件匣現有筆記依分類併入正式資料夾、更新索引、寫每日復盤。

不確定要跑哪個模式時，預設 capture；使用者或排程明確要求「整理收件匣」「consolidate」「每日整理」時跑 consolidate。

## 共用前置

1. 讀 `AI_ENTRY.md` 與 `00-系統/寫入規則.md`，確認規則沒變。
2. 判斷本次執行情境：**互動對話中**（使用者當下在場）或 **排程／背景執行**（無人即時應答）。這個判斷會決定後面「核准流程」該走哪個分支——見 `references/approval-flow.md`。

## Capture 模式

1. **定範圍**：預設蒸餾「上次呼叫 save 之後到現在」的新內容；無法判斷上次呼叫時間點時，蒸餾整個當前對話／任務。避免同一段內容被重複蒸餾兩次。
2. **任務類型分類**：
   - 純問答／沒有新事實 → 跳過，回報「無新增」，結束。
   - 單一小決策或單一專案更新 → 走完整流程，索引維護只動一行。
   - 多專案／高影響變更 → 走完整流程＋索引維護＋額外檢查是否也影響其他專案既有筆記（交叉引用）。
3. **擷取候選內容**：只留跨任務價值的——穩定偏好、可重複工作流、已確認規劃、影響後續的決策、專案現況／阻礙／下一步。排除完整對話、終端輸出、臨時推測、Git 可重建的程式碼、機密值。
4. **分類**：套用 `references/classification-taxonomy.md`，不得自創類別。
5. **查重**：套用 `references/classification-taxonomy.md` 裡的「搜尋下限」——先讀對應索引檔，命中才展開讀全文，再補一次自由關鍵詞搜尋。
   - 語意已存在 → 不寫入，回報「無新增：與 [[既有筆記]] 重複」。
   - 部分重疊 → 只寫新增的部分，`related` 連結既有筆記。
6. **判斷風險等級**：刪除、合併、覆蓋、衝突、規則升級（偏好→強制規則）、改變既有資料夾結構，這六類屬於高風險，套用 `references/approval-flow.md`，不得直接執行。純新增則直接進第 7 步。
7. **寫入**：依 `references/frontmatter-schema.md`，新增 `01-收件匣/YYYYMMDD-HHmmss_Agent_專案.md`，不得覆寫既有檔案。
8. **索引維護**：純新增一行到對應索引檔（見下方「索引維護規則」），不需核准。
9. **回頭掃描待確認清單**（見下方）。
10. **完成檢查**（見下方 Capture 版）。
11. **回報**：新增了什麼、跳過了什麼重複、有什麼在等核准、索引更新了什麼。

### 收工交接（強制）

當使用者明確說「收工」、「任務結束」或同義語時，除了 Capture 的一般蒸餾外，必須建立一份可供下一次工作直接接續的收工交接。即使本次工作已在過程中分批 capture，也不能只回報「沒有新內容」；應彙整自上次收工以來的整個工作階段，必要時以 `related` 連結既有 capture，避免重複抄寫細節。

收工交接必須包含以下四個固定章節；沒有內容時明確寫「無」，不得省略：

```markdown
## 今天完成

## 尚未完成

## 下一步

## 注意事項
```

- **今天完成**：記錄已實際完成並驗證的成果與已確認決策，不寫操作流水帳。
- **尚未完成**：記錄仍待實作、待驗證、待部署、待補素材或待使用者決定的事項。
- **下一步**：寫出下一次接手時最先應執行的具體動作；若有多項，依優先順序排列。
- **注意事項**：記錄已知問題、不可違反的限制、評鑑或部署狀態、必要路徑與其他可能造成重工的資訊。

交接內容屬專案現況時使用 `category: 專案`；跨專案工作才使用相應分類。完成寫入後，在回報中明確說明交接檔已建立及涵蓋的工作階段。

## Consolidate 模式

1. **列清單**：讀 `01-收件匣/` 目前所有筆記（排除 README.md）。
2. **逐篇處理**：
   - 依 frontmatter 的 `category` 找目標正式檔案（`references/classification-taxonomy.md` 的資料夾對應）。
   - 查重：目標檔案是否已有語意相同內容 → 有則不重複寫入。
   - 純新增或延伸既有段落 → 併入正式檔案，用 `## YYYY-MM-DD：主題` 分段（比照 `決策索引.md` 現有寫法）。
   - 跟正式檔案內容衝突、需要覆蓋或合併 → 不直接執行，套用 `references/approval-flow.md` 寫入 `40-決策紀錄/待小威確認.md`；原收件匣筆記保留、標記「待確認，尚未合併」。
3. **移動來源**：已合併（含「無新增」判定）的筆記移至 `90-每日復盤/來源封存/YYYY-MM-DD/`；未合併（等待核准）的留在收件匣。
4. **寫每日復盤**：`90-每日復盤/YYYY-MM-DD.md`，含新增長期記憶、專案進度、已確認決策、待小威確認、來源清單（連結封存位置），格式比照既有檔案。
5. **索引維護**（見下方）。
6. **回頭掃描待確認清單**（見下方）。
7. **完成檢查**（見下方 Consolidate 版）。
8. **回報**：合併了幾篇、跳過幾篇重複、有幾篇等核准、索引更新狀況。

## 索引維護規則

純新增一行到對應索引，**不算高風險操作、不需要核准流程**，但只能新增、不能刪改既有行：

- 新專案第一次出現在 `50-專案記憶/` → `專案索引.md` 加一行連結。
- `90-每日復盤/` 新增一篇 → `每日復盤索引.md` 一定要加一行（最容易漏加，每次都要檢查）。
- `40-決策紀錄/` 新增一個以前沒被索引提及的獨立主題 → `決策索引.md` 視需要加註。

## 回頭掃描待確認清單

完成檢查前，讀一次 `40-決策紀錄/待小威確認.md`，確認這次任務／對話有沒有剛好回答掉裡面某個舊項目；有的話標記該項目已解決（移到對應正式決策位置或標註解決方式與日期），不留孤兒項目。

## 完成檢查

**Capture**：新檔可讀、路徑正確、未覆寫同名檔／frontmatter 完整符合 schema、來源可追溯／未寫入機密、臨時內容或 Git 可重建的程式碼／索引若需要更新已更新／待確認清單已掃描過。

**Consolidate**：每篇收件匣筆記都有明確結果（已合併／已判定重複／已轉待確認），沒有筆記被遺漏／已合併的來源都正確移到來源封存／每日復盤摘要已寫入且格式一致／三個索引檔狀態正確／未合併項目都能在待確認清單或收件匣中被找到，沒有資訊憑空消失。

## 明確排除範圍

- **知識庫健康稽核**（dead link、孤兒 skill、junction 是否生效）——獨立稽核型技能的工作，不是 save 的核心迴圈。
- **協調 Claude Code 專案原生 memory 與本知識庫的分工規則**——系統性問題，另外訂規則。
- **機密資料處理**——完全不碰 `60-機密/`，沿用既有規則。
