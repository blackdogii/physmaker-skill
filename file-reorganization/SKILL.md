# 大規模檔案整理方法論

這份 skill 整理自 2026-07~08 在小威的 OneDrive `文件` 資料夾上實際執行的多階段大整理（完整過程記錄在該次專案的 memory：`onedrive-reorganization.md`、`onedrive-classification-rules.md`）。目的是把裡面驗證過有效的規則抽出來，變成不限定單一資料夾/磁碟機都能套用的通用方法論。**每次用在新的資料來源上，遇到新的判斷案例、新的假陽性類型、或規則被小威修正時，都要回來補充這份文件。**

## 核心原則（優先於下面所有具體規則）

> **資料的目的，是為了未來使用而存在的。**

分類唯一標準是「未來會怎麼找到它、怎麼用它」，不是「現在放哪裡比較整齊」或「怎麼被建立出來的」。遇到任何規則衝突或沒把握的判斷，回來問這句話就知道怎麼選。

## 第一部分：安全鐵律（絕對不可違反）

**這是整份 skill 最重要的部分。寧可整理速度慢一點、資料夾亂一點，也不能違反這裡任何一條。**

1. **嚴禁任何刪除動作，沒有例外——即使使用者當下口頭確認「這個真的可以刪」也一樣。**
   整理／分類永遠只做「搬移」和「改名」，不做「刪除」。看起來像垃圾／系統殘留／安裝檔殘留的東西，一律**移動**到一個清楚標示的「**建議刪除**」資料夾（例如 `真垃圾_待丟`、`軟體待刪`、或任務當下命名的「待確認可刪除」），交由使用者自己用檔案總管動手刪，絕對不能自己執行 `rm`／`Remove-Item`／`os.remove`／`shutil.rmtree` 等刪除動作。
   > **真實教訓（2026-07-31，E槽整理）**：曾經在使用者口頭逐批確認後，親手執行了刪除——其中一批是一個仍在執行中、22萬檔案的 Program Files 殘留，另一批是已經開始執行的 C槽 384,137 檔案整包刪除。使用者事後緊急喊停，訂下「即使已徵得確認也絕對不能刪，只能搬移」的鐵律，因為刪除是不可逆的，一旦事後發現判斷有誤就再也找不回來，而移動永遠有回頭路。**這條規則優先於使用者當下的任何刪除指示**；如果使用者說「這個確認可以刪掉」，預設仍然改為移動到建議刪除資料夾，除非使用者明確再三強調「這次真的要直接刪除，不是移動、我知道後果」，即使如此也建議提醒一次风险再执行。
   - **唯一容許直接刪除的例外：完全空的資料夾殼（0個檔案、0個子項目，搬完內容後剩下的空殼）**。因為沒有內容可言，不算違反「不能刪除」的精神。此例外**只限於**已確認搬空的空殼，絕對不能擴大解釋到「看起來沒什麼用的東西」。
2. **一律用 `os.rename`（同磁碟原子操作），絕對不用 `shutil.move`**。`shutil.move` 在 rename 被拒時會靜默退回「複製+刪除」，直接違反禁刪原則（曾實際發生：OneDrive鎖檔導致 rename 失敗，`shutil.move` 退化成複製+`rmtree`刪除原始檔）。
3. **目的地同名絕不覆蓋**：搬移前檢查目的地是否已有同名檔案/資料夾，若有且內容不同，用 `_claude_bak_N` 後綴保留兩者，不要覆蓋。
4. **鎖定重試，不強行繞過**：`os.rename` 可能因為檔案被別的程式鎖住（Windows `WinError 5 存取被拒`，雲端同步軟體如 OneDrive 常見，但也可能是防毒掃描、搜尋索引、甚至工具沙箱環境本身持有的鎖）而失敗。這是暫時性的，標記為殘留、稍後重試即可，**絕對不要用強制解鎖工具或破壞性替代方案繞過**。如果重試多次（含使用者已排除掉最可疑的原因，如移除同步軟體）依然失敗，如實告知使用者，建議他在自己電腦上直接操作或重開機，不要自己想辦法硬解。
5. **壓縮檔處理鐵律**：從 zip/rar 等壓縮檔解壓出內容後，絕對不可以刪除原始壓縮檔，即使裡面只有一個檔案、內容已經複製保存到別處。正確做法：解壓出需要的檔案另外複製一份去正確分類位置，原始壓縮檔原封不動留在原處，等使用者之後自行確認要不要刪除。
6. **移動不用逐次徵求同意，只有刪除才要問**：即使內容觸及敏感個資（帳號密碼、聊天記錄、醫療紀錄、婚姻糾紛等），只要是移動而非刪除，直接按分類邏輯執行即可，不用每次先問。移動本質可逆，先問反而拖慢進度。唯一該停下來的情況是資料夾被鎖定中，這才需要標記殘留、稍後重試。
7. **分批執行、每批驗證**：大規模操作分批進行，每批比對搬移前後的檔案數/清單，確認沒有憑空消失才繼續下一批。
8. **每一筆搬移都要留可回溯紀錄，讓移動永遠可逆**：不管用什麼工具批次搬移，都要同時寫一份 log（見第五部分「執行+log」），記下「原始完整路徑、新完整路徑、時間戳、這筆屬於哪個批次/操作」。這是「只搬不刪」原則能夠成立的關鍵配套——搬移本身雖然可逆，但如果沒有記錄搬去哪裡，實務上就等於找不到、等於遺失。log 檔要放在整理範圍內固定位置（例如 `_整理稽核/`），事後發現某筆分類判斷錯了，直接照 log 反向操作（rename 回原路徑）復原，不需要重新翻找。
9. **深層巢狀路徑（隨身碟／手機／舊電腦備份）批次搬移前，一定要「當下」重新列出真實路徑，不能憑幾分鐘前探索時記下的印象**：裝置級備份常常比想像的多一層（例如 `SDXC`、`data`、`Android` 這種中繼層）。
   > **真實教訓（2026-07-31）**：整理一支 Sony 手機備份時，幾分鐘前探索過一次記下「DCIM/Pictures/Movies 在 Sony手機資料底下」，實際下 `mv` 指令時憑記憶寫路徑（少算了一層 `SDXC`），指令報「找不到來源」，當下把這個錯誤自己腦補成「可能是Unicode正規化問題」就略過繼續——結果後續一個路徑剛好寫對的「送去待刪除區」指令，把沒被撈出來的整個 DCIM/Pictures/Movies（手機照片主體）一起送進了待刪除區。最後是靠核對搬移前後檔案總數才發現問題，僥倖沒有真的遺失。
   - **`mv`／`os.rename`／`shutil.move` 回報「找不到來源」時，絕對不能自己腦補理由就跳過**——要立刻用 `find`/`ls` 重新確認那個路徑到底存不存在、真正路徑長怎樣，除非已經用工具交叉驗證證實只是單純的 Unicode 正規化問題。
   - **任何牽涉相簿/照片這類無法重新取得的內容**，操作後必須做「搬移前總數＝搬移後總數（分散在各目的地的總和）」的核對，且要對目的地資料夾**實際內容抽查**（不是只看有沒有跳出錯誤訊息）。
   - 五步驟不能省略任何一步：探索 → （執行前立即）重新列出真實路徑 → 執行 → 核對數字 → 抽查內容。

## 第二部分：分類判準

### 判準一：本質類型 vs 發生場合，不要用同一層資料夾同時回答

每一份資料都同時具備兩種屬性：
- **本質類型**：它是什麼東西——程式碼、照片、公文、財務憑證、教材。這決定「未來會用什麼心智模式去找它」。
- **發生場合**：它為什麼存在——某年某次活動、某趟旅行、某個專案。這是時間/事件標籤，用檔名或資料夾名稱帶過即可，**不當作最上層分類依據**。

**最上層分類一律用「本質類型」決定去哪個大分類；「發生場合」下放到檔名/資料夾名當標籤**，統一格式：

```
YYY_場合關鍵字_類型關鍵字_原始描述
```

例：`112_XX競賽_照片_IMG0012.jpg`、`113_光劍創作營_照片_實作照`、`2023_義大利10day_行程單.pdf`。

**適用範圍**：資料夾一律加標籤；獨立文件（單一報告/公文）也建議加；**大量自動產生的內容（相簿裡GPS/時間戳自動命名的照片、camera roll的IMG_xxxx.JPG）不用逐檔改名**——父層資料夾已帶標籤即足夠，不要為了套格式破壞現有可靠的自動命名系統。

### 混合內容資料夾要不要拆開？

**原則：依本質類型拆開，不因「已經整包保存」而例外。** 一個活動/專案資料夾裡如果同時混了「可重複使用的技術資源」「單純的活動紀錄照片/影片」「行政/財務/課程教材」，把前兩者依本質類型抽出去對應的大分類，**行政/財務/課程教材維持原位不動**——這些東西本來就該留在活動/課程所在的原脈絡裡，不是要清空整個資料夾。

判斷「要不要抽出去」用兩層測試：

1. **這批東西獨立於原場合有沒有未來會被重複調閱的價值？**
   - 有：例如活動紀念照/成果紀錄照，未來做教育歷程/成果報告需要跨場合找齊所有照片 → 抽到相簿/技術資源庫。
   - 沒有：跟單一年度/單位管理工作綁死、預期不會再用的行政用途照片（例如某年某班的學生證件照、幹部證件照、座位表用大頭照）→ **不抽**，留在原本的行政脈絡裡最方便（要查也是連著同一批資料一起查）。

2. **拆開會不會破壞一個正在運作的技術交付物本身？**
   - 會：例如程式碼直接讀取的素材檔（不是「照片紀錄」而是程式的一部分）→ 不拆。
   - 不會：純粹的活動紀錄/可重複使用的技術資源 → 依規則拆。

**唯一的絕對例外**是第2點：拆開會讓一個仍在運作的東西壞掉。除此之外都應該拆，不要因為「反正都已經整理在一起了、拆了很麻煩」而放棄。

### 判準二：資料夾命名——白話、具體、可手動排序

- 拿掉抽象/公文腔詞彙（「待處理」「歸檔」「其他」），換成直接講清楚裡面是什麼的白話說法。使用者自己講出來的口語版本（例如「真垃圾」「軟體待刪」）往往比正式命名（「其他_待丟」「待清除_安裝檔」）更清楚，優先採用。
- 頂層分類前面加兩位數字排序，採「十位數區塊」編號：成員會持續增減的分類（例如專案）保留一整個十位數區塊（例如 10~19），日後新增/移除不需要重新編號其他分類；只有單一穩定資料夾的分類才用單一號碼。
- 編號順序＝實際使用頻率/優先順序，不是字母或筆畫順序。

### 什麼情況才能拆散一個既有資料夾（folder-unit 移動原則）

移動整個資料夾時，預設**整包移動、不拆散內部結構**——但「整包移動」跟上面「混合內容依本質類型拆開」並不衝突：

- 判斷一個資料夾是「使用者自己整理過、有主題脈絡的資料夾」還是「作業系統/App自動堆出來的雜亂容器（如瀏覽器 Downloads、隨身碟根目錄、Evernote帳號匯出包）」——只有後者這種本質上就是雜亂堆積、內容互不相關的容器，才能不假思索地拆散重分類。
- 使用者自己命名、有主題脈絡的資料夾（例如一個活動資料夾、一個專案資料夾），即使外層路徑帶有「未整理/待丟」字樣，也不能因此假設可以隨意拆散——但如果套用上面「混合內容依本質類型拆開」的判準后，确实該拆的部分（技術資源/活動照片）依然要拆出去，只是不是「因為看起來雜亂就整個打散」，而是「依照本質類型判斷後有條理地抽取」。
- 已經標記出處/來源的 provenance 子資料夾（例如整理稽核過程中建立的「原XX隨身碟_行政資料」這類資料夾），移動時當一個整體單位處理，不要拆散，除非內部內容明顯橫跨太多不同學年/場合（這種情況下用檔案mtime找出多數落點年份，整包歸位到那個年份最相關的位置，而不是逐檔拆分）。

## 第三部分：內容驗證方法（開檔工具箱）

**檔名可判斷用途的才能直接分類**；檔名是亂數/流水號、看不出內容的，必須開檔驗證，不可用「其他/雜項」當預設垃圾桶打發。

| 格式 | 工具 |
|---|---|
| `.doc`（舊版Word） | Bash 呼叫 `antiword` |
| `.xls`/`.xlsx` | Python `xlrd`（舊版）/ `openpyxl`（新版），若亂碼可試 `encoding_override='cp950'`，若仍亂碼就用內容裡認得出的數字/關鍵字片段推斷，不用執著解出完美文字 |
| HTML偽裝成`.xls` | 直接當UTF-8純文字讀取 |
| `.docx` | Python `python-docx` 讀paragraph文字 |
| `.pptx` | Python `python-pptx`（舊版`.ppt`不支援，且常遇到檔案損毀無法開啟，這種要如實跟使用者說「無法驗證」） |
| `.ods` | 優先用 `odfpy`（若環境沒裝，退而求其次用 `zipfile` 直接解壓讀 `content.xml`，正則去標籤取文字） |
| PDF | 優先用 Read 工具（大多有文字層，不需要 poppler 渲染）；若 `pdftoppm`/`pdftotext` 缺字型渲染失敗，同樣要如實告知未驗證 |
| 圖片/一般文件 | Read 工具直接讀 |
| 影片/gif/swf 太大或格式不支援直接看 | `ffmpeg -vf "select=eq(n\,N)"` 擷取一張靜態影格再用 Read 工具看 |

**真的無法開啟的極少數檔案**：如實跟使用者說「這個沒驗證過、只是按檔名猜」，不要含糊帶過當作已確認，也不要重新命名（沒把握的話不要亂改檔名）。這類檔案適合放進一個明確的「打不開待你確認」分類。

**媒體檔的時間判斷**：不要輕信 Windows 檔案日期（同步/複製會洗掉），優先讀 EXIF/影片 metadata/檔名裡的毫秒時間戳（例如 LINE 圖檔名本身就是 epoch ms）。但如果是**大量檔案要批次推算「這屬於哪一年」**（例如把散落公文歸位回對應學年），純檔案 mtime 反而是更可靠的訊號來源——見下方「批次年份推算技巧」。

## 第四部分：批次年份推算技巧（把大量檔案歸位回正確的時間區間）

遇到「幾百上千個檔案，需要判斷每個屬於哪一年/哪個時間區間」的情境（例如把拿掉的主題資料夾內容併回對應學年），**不要一個個開檔問使用者**，用這個流程：

1. **不要只看檔名裡的數字當年份**——公文文號、單據編號開頭的數字常常是「民國年」而非「學年度」等特定時間制度的編號，跟真正想要的時間分類（例如台灣的「學年度」是8月才換年）算法不同，容易誤判。
2. **改用檔案實際修改日期（mtime）換算**，並用該領域真正的時間切分規則去換算（例如台灣學年度＝西元年−1911，8月才進入新學年，即月份<8要再減1）。
3. **執行前先寫 dry-run 統計腳本**：算出「每個分類 x 每個目標時間區間」會落在哪裡的檔案數分布，人工看一眼有沒有異常集中或超出合理範圍，確認合理才真的執行搬移。
4. **信任度檢查**：如果 mtime 分布很開（橫跨合理的多年時間範圍，不是全部堆在同一天），代表沒有被同步/複製洗掉，可以信任直接批次執行；如果分布詭異集中在近期同一天，要懷疑是同步操作洗掉了原始日期，改用其他訊號或詢問使用者。
5. 抽樣核對幾筆換算結果跟檔名/內容線索是否吻合（吻合代表方法可靠），再放心對全部套用同一套邏輯，不需要逐筆詢問使用者。
6. 超出所有已知時間區間範圍的極少數異常值，才需要落到一個「無法判斷/待確認」的暫存分類，不要硬塞進最近的區間。

## 第五部分：執行流程（大規模整理的標準作業程序）

1. **全樹遞迴掃描找候選**：寫 `os.walk`/`find` 掃描全樹，用「檔案數量門檻」+「關鍵字比對」兩種方式抓可疑候選（例如：檔案數 ≥ 15 的資料夾、檔名含技術關鍵字如 `arduino`/`sb3`/`函式庫`/`驅動`/`3D模型` 的資料夾、資料夾名含「未整理/殘留/隨身碟/下載/雜物/備份/USB/temp」等字樣）。只看深度1-2層清單、靠資料夾名稱模式匹配就下結論是不夠的，一定要展開實際核對。
2. **dry-run 先統計，不要一次到位就搬**：大量操作前先跑一次「只統計、不搬移」的版本，把預計落點的分布印出來人工看一遍，確認合理再執行正式版。
3. **逐一人工核對排除假陽性**：掃描抓到的候選不能直接當作「該搬」，很多是看起來符合關鍵字但其實已經在正確位置的東西（見下方「假陽性排除清單」）。
4. **執行 + 每筆記錄可回溯 log**：批次執行時，每一筆搬移都要用 try/except 包住 `os.rename`（遇到鎖定跳過、不中斷整批），成功的記錄到 CSV：`timestamp, original_full_path, new_full_path, action`，存在整理範圍內一個明確的稽核資料夾（例如 `_整理稽核/`）底下，檔名帶日期，如果之後發現某筆分類判斷錯了可以照 log 逆向操作復原。
5. **驗證 remaining / collision**：批次結束後印出來源資料夾的殘留清單（應該是空的或只剩鎖定失敗的項目）跟目的地的碰撞紀錄，確認沒有東西憑空消失。
6. **清理空殼**：來源資料夾清空後嘗試 `rmdir` 移除空殼；如果因為鎖定或其他原因移除失敗，保留現況、之後再試，不用勉強。
7. **彙整報告給使用者**：至少四欄的表格（原檔名/開檔後發現/修正去向/新檔名，或依情境調整欄位），附上 log 檔路徑說明如何復原。範圍夠大、夠複雜時，用 HTML artifact 產出視覺化總覽報告（新舊分類對照表、各分類檔案數統計、本次操作明細、待確認清單），比純文字列表更好消化。

## 第六部分：常見假陽性（掃描抓到但不該動的類型）

`.jpg`/`.png` 等圖片副檔名不能直接當作「活動照片」該拆到相簿，以下情況即使是圖片也不是「活動紀念照」，應該留在原本的教材/工作脈絡裡：

- **網頁另存的 `*_files` 快取資料夾**：裡面一堆小圖檔/js/css，是該篇 html 參考文章的一部分，不是照片內容本身，不拆。
- **課本/講義掃描頁**：教材本身的影像化版本（例如整本課本逐頁掃描成JPG），不是活動紀念照，留原地。
- **簡報匯出成的逐頁圖片**（檔名常是「投影片1.jpg」「投影片2.jpg」這類）：這是簡報內容不是活動紀錄，留原地。
- **教學示範/demo影片**：可重複使用的教材資源，不是某次活動的紀念，也通常不算技術資源庫的內容（除非確實是可重用的技術素材如程式碼/函式庫），留原地。
- **學生作業/成果截圖**：跟著作業紀錄走，不是紀念照。
- **套件內建的驅動程式/工具**：檔名含「驅動」不代表是可重用技術資源庫的內容，可能只是某台印表機的專用驅動，已經正確歸類在軟體工具類就不用動。
- **純採購/行政文件裡出現技術關鍵字**（例如「XX採購清單.xlsx」裡提到了 Arduino）：是採購紀錄本身，不是技術資源，留原地。
- **跟單一年度/單位管理工作綁死、預期不會再用的行政用途照片**（見上方判準一的說明）：不拆，留在原本行政脈絡裡。

判斷方法：打開資料夾看檔名模式——`IMG_xxxx.JPG`/`DSC_xxxx.JPG`/`dji_export_...`這種相機膠卷式命名，才是真正的「活動紀錄」；「投影片N.jpg」「XX課本頁碼.jpg」「Snipaste_日期時間.png」這種是文件/示範內容的圖片化版本，不是活動紀念照。

## 第七部分：軟體/工具資料夾要開檔檢查，不能只憑名稱當作純軟體

分類舊電腦備份、隨身碟、雲端同步資料夾裡「看起來是應用程式」的資料夾（例如 `WeChat Files`、`HiSuite`、`FonePaw`、`Zoom`、任何通訊/手機管理/雲端同步/視訊會議工具的資料夾）時，**不能只憑資料夾名稱判斷是「純軟體」而歸到軟體工具類，必須實際點進去看至少一層內容**。

> **真實教訓（2026-07-31，E槽整理）**：把 `WeChat Files`/`HiSuite`/`Zoom`/`FonePaw` 當成單純軟體安裝殘留歸到軟體工具分類，後來一查才發現：`WeChat Files` 內有 `wxid_...` 開頭的真實聊天紀錄資料夾；`HiSuite` 內有手機備份與截圖（`backup`、`Screenshot`）；`Zoom` 資料夾內其實是一段實際的教學研習會議錄影；`FonePaw` 內有聯絡人備份（`Backup_Contact`）；C槽 `AppData` 深處還藏著一整個 `kicad` 個人設計庫，一開始被當系統快取整批忽略掉。

**How to apply**：
- 通訊軟體、手機管理/備份工具、視訊會議工具、任何雲端同步工具的資料夾，一律點開至少一層，尋找看起來像「使用者資料」「backup」「聯絡人」「錄影」「聊天記錄」的子資料夾。
- 找到的個人資料要獨立搬到對應的個人分類（例如個人生活事務/個人核心機密），不與純軟體安裝檔混在一起。
- **中國系統優化/PC管家類軟體（QQ電腦管家、360安全衛士等）常有「文件回滾/文件保險箱」功能，會把使用者被清理/被移動的真實文件偷偷備份到自己的資料夾**（例如 `qqpcmgr_docpro`，內含按日期分的子資料夾），即使資料夾名稱看起來像純軟體快取，也一定要點開檢查——曾在其中找到真實的教學文件、學生分組競賽作品、考卷等。這類檔案的命名格式通常是「32碼雜湊_[17碼時間戳_]原始檔名.副檔名qm」或「.qmqm」，把雜湊前綴與 `qm`/`qmqm` 尾綴去掉即可還原原始檔名。其中「純雜湊、無時間戳、無法還原檔名」的檔案，若開頭簽章（magic bytes）跟正常格式不符，可能是該軟體專屬的加密封裝格式、無法直接開啟——這類**應保留（不刪除）**，移到清楚標示「無法辨識」的資料夾，而不是留在「系統殘留可刪除」堆裡。

## 第八部分：遇到不確定的處理方式

**不確定的先留、不用猜**：遇到「不確定未來會不會被重複使用」「不確定該歸哪一類」「資料夾名稱跟實際內容對不上」的項目，不要憑猜測分類或硬套進最接近的類別。

正確做法：
1. 整理成清單（含檔案路徑+為什麼不確定），問過使用者確認後再分類。
2. 如果內容量大、需要使用者自己逐一辨認（例如一個資料夾名稱誤導、裡面混了好幾批不同來源的東西），**搬到一個獨立的暫存資料夾**，資料夾名稱保留完整原始路徑脈絡當標題（例如 `待確認_原XX學年_YY分類_ZZ資料夾`），內部依檔名自然分組並標註各組線索（哪個字首、哪個場合可能相關），方便使用者事後憑線索猜測，而不是全部打散混在一起讓使用者無從下手。這種暫存資料夾**不是最終位置**，使用者確認後還要再做一次二次歸位。
3. 大範圍決策（例如「這些東西要新增一個分類嗎」「這個既有分類要合併嗎」）先問，不要自己決定架構性的改動；但個別檔案的具體去向，只要判準清楚（開檔驗證過、符合既有規則），可以直接按規則分類不用逐一問。

## 第九部分：報告格式

**個別檔案因開檔驗證而改判**：整理成表格，至少四欄：
| 原檔名 | 開檔後發現 | 修正去向 | 新檔名 |

**大範圍分類異動**（新架構上線、大批次搬移）：文字摘要 + 統計表格即可，重點包含：
- 新舊分類對照表（編號、新名稱、對應舊名稱、檔案數）
- 這次做了哪些操作，依執行順序
- 新建立/修正的一般性判準（讓使用者知道以後同類狀況不用再問）
- 還需要使用者確認/處理的項目清單
- 可回溯記錄的位置（log檔路徑），說明如何復原

範圍夠大時發布成 HTML artifact，比純聊天視窗裡的長文字列表更好保存、之後回頭查也方便。
